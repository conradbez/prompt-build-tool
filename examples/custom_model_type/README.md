# Custom model types

Every `.prompt` file is run by a *model type*. This example registers one of its
own, alongside two built-in ones.

```bash
export GEMINI_API_KEY=your_key_here
pbt run
pbt run --promptdata topic="deep sea mining"
```

## What is here

| File | Model type | What it does |
|---|---|---|
| `models/article.prompt` | *(none)* | An ordinary model — the rendered prompt goes to the LLM |
| `models/headline.prompt` | `shout` | Custom: calls the LLM, then uppercases the answer and appends `suffix` |
| `models/length.prompt` | `execute_python` | Built-in: runs the template as Python instead of calling the LLM |
| `models/report.prompt` | `template` | Built-in: renders Jinja and returns it, no LLM call |
| `client.py` | — | Registers the `shout` type, and defines `llm_call` |

Run it and `outputs/report.md` looks like:

```markdown
# TIDAL ENERGY: A PREDICTABLE CLEAN POWER SOURCE WITH GROWING POTENTIAL!

Tidal energy is a renewable power source generated by the natural rise and
fall of ocean tides, which are driven primarily by the gravitational pull of
the Moon and the Sun...

_(173 words)_
```

The headline is uppercase and ends in `!` because the `shout` kind did that to
the LLM's answer. The word count came from `execute_python`, which never called
the LLM at all — you can see it and `report` finish in ~0 ms in the run output.

## How a custom kind is written

One function, registered by name:

```python
# client.py
import pbt

@pbt.model_kind("shout", config_keys={"suffix"})
async def shout(rendered, call):
    response = await call.llm(rendered)
    return response.upper() + call.spec.config.get("suffix", "")
```

Then any model can ask for it:

```jinja
{{ config(model_type="shout", suffix="!") }}
Write a single short headline for this article.

{{ ref('article') }}
```

pbt renders the template for you. `rendered` is that text; `call` carries what
you might need with the model already bound — `call.llm(rendered)` sends it to
the backend (cached, timed, skip-aware), `call.spec` is the model being run
(`call.spec.name`, `call.spec.config`), and `call.outputs` holds upstream
outputs by name.

Whatever you return becomes the model's output: what `ref()` gives downstream
models and what lands in `outputs/`.

`config_keys={"suffix"}` tells pbt that `suffix` is a real option. Without it,
`pbt run` warns that it looks like a typo.

## Before writing a type, check the built-in ones

`length` counts the words in the article, and needs no custom type at all —
`execute_python` runs the template as Python:

```jinja
{{ config(model_type="execute_python") }}
output = len(ref('article').split())
```

The template is rendered first, then the result is executed. `ref('article')`
here is a plain Python call at run time, and it is also what puts the edge
`article -> length` into the DAG.

Reach for a type of your own when the behaviour is something you want to reuse
across models and configure per model, the way `shout` takes a `suffix`. For a
one-off calculation, `execute_python` is less code.

## What you get for free

Your type behaves like a built-in one. The prompt cache, `output_format="json"`
parsing, the skip functions, `validation/`, `pbt test`, `pbt docs` and the run
report all work without any extra code.

## Where registration goes

`client.py`, because pbt already imports it on every `pbt run`, `pbt test` and
`pbt ls` — before it reads your models. Anywhere earlier works too.

See the README section *Writing your own model type* for the remaining hooks:
caching non-LLM work, opting out of the global instruction, and expanding one
model into several.
